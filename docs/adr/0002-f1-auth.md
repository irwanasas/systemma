# 0002 — F1 auth decisions

Status: accepted

## Decisions

- `/change-password` lives at `app/change-password/` (outside the role groups) so admins and agents can both use it; the URL is unchanged. Approved at the F1 checkpoint.
- Usernames: 3–32 characters, lowercase letters, digits, `.`, `_`, `-`; stored lowercase. Passwords: 8–72 characters (bcrypt ignores bytes past 72).
- Agent codes are stored uppercase.
- Agent creation goes through the SQL function `create_agent` so the `users` and `agents` rows are written atomically. It is not `SECURITY DEFINER`; only the service role can execute it.
- Default privileges: new tables, sequences and functions in `public` get no grants for `anon`/`authenticated`, and new functions get no `PUBLIC` execute. pgTAP checks this for every table and app function.
- Sliding session renewal: `getCurrentUser()` extends `sessions.expires_at` on every request; `proxy.ts` re-sets the cookie's max-age because Server Components cannot set cookies.
- Unknown usernames still run a bcrypt compare against a fixed hash, so response time does not reveal which usernames exist.
- Rate limiting counts failed `login_attempts` per username + IP (`x-real-ip`, else the first `x-forwarded-for` entry, else `NULL`) in the last 15 minutes. A deactivated account with a correct password also counts as a failure.
- Changing a password deletes the user's other sessions. Admin password reset and deactivation delete all of the agent's sessions.
- Deactivation asks for confirmation; there is no reactivate action yet.
- Seed passwords: `[db.seed]` is disabled in `supabase/config.toml` because the CLI hides `RAISE NOTICE`. `npm run db:reset` resets and then runs `seed.sql` through `psql`, which prints each generated password once.
- CI and local e2e use the Supabase CLI's public local demo service-role key; it only works against the local stack.
- `npm run db:start` starts only the database, PostgREST and Kong (the app needs PostgREST; Supabase Auth is not used).
